# 浏览器：逐配置清理与核验

这是给执行 AI 的操作参考。先完成主流程的只读盘点、范围计划和用户确认，再执行删除。
清理用于移除本机登录状态，不解除 Claude 服务端封禁，也不保证以后不会被封。
不得为此修改 IP、时区、硬件标识、浏览器指纹、代理或浏览器安全功能。

## 1. 建立完整清单

1. 识别当前操作系统、实际安装的浏览器和可用的原生 UI 工具。
2. 在当前系统用户范围内只读枚举浏览器配置，不能只检查当前窗口。
3. 把 UI 显示名与磁盘配置目录对应起来；二者可能不一致。
4. 一个 Google 登录账号不一定等于一个 Chrome 配置。以实际配置目录和窗口为准。
5. 记录每个配置的浏览器、显示名、目录、是否运行、是否受组织管理，以及核验能力。
6. 只盘点用户授权范围内的配置，不自动进入其他系统用户的目录。

Chromium 常见数据根位置仅供定位，必须检测实际存在的路径：

| 平台 | Chrome | Edge / 其他 Chromium |
|---|---|---|
| macOS | `~/Library/Application Support/Google/Chrome` | 查询对应产品的数据目录 |
| Windows | `%LOCALAPPDATA%\Google\Chrome\User Data` | 查询对应产品的数据目录 |
| Linux | `~/.config/google-chrome` | 查询对应产品的数据目录 |

用 Chromium `Local State` 中的配置清单辅助对应，不能因为目录名称类似就全部删除。
Mac / Windows 可运行 `scripts/browser_inventory.py` 做只读辅助盘点，Windows 用 `py -3`。Windows Edge 根为 `%LOCALAPPDATA%\Microsoft\Edge\User Data`，Brave 根为 `%LOCALAPPDATA%\BraveSoftware\Brave-Browser\User Data`，Firefox 从 `%APPDATA%\Mozilla\Firefox\profiles.ini` 的实际配置清单定位。脚本不输出账号邮箱、Cookie 值或密码，也不删除网站数据；Firefox 仅列配置，Safari 需使用原生设置。
Cookie 数据库可能在配置根的 `Cookies`，也可能在 `Network/Cookies`。
同一配置存在多个候选时，核查实际使用位置并记录；不要自行选一个后声称全部完成。
本包的真实账号执行经验来自 macOS Chrome；两平台的浏览器盘点用隔离数据库测试域名边界和只读行为。Windows / 其他浏览器的实际网站删除仍按现场 UI、路径和数据库结构分支，不能由测试推断所有版本的登录数据已清理。

## 2. 确认精确目标

默认网站数据目标只有以下官方域及其子域：

- `claude.ai`
- `claude.com`
- `anthropic.com`

判断条件为规范化主机名 `h == d` 或 `h.endswith('.' + d)`。
Cookie 主机名可先去掉前导点并转成小写；URL 应先解析 hostname，不能对整个 URL 做包含匹配。
`upclaude.com`、`notclaude.ai.example.org`、包含 Claude 字样的第三方服务都不符合条件。
不要删除整个 `cloudflare.com`、`google.com`、邮件域名或所有 SSO 网站的数据。
其他供应商、镜像站或第三方账号工具，须先显示其确切域名和用途，再取得对应范围确认。

主流程的确认计划应列出：

- 将处理哪些浏览器配置和官方域名。
- 网站数据删除将退出这些网站，并移除本地离线数据和相应权限。
- 将移除哪些已核实的 Claude 扩展实例，及其独立存储。
- 浏览器 UI 删除通常不可撤销；是否有受保护的恢复副本。
- 书签、密码、Google 账号、其他网站数据和浏览历史默认保留。

用户对计划的明确确认可覆盖这一批原生 UI 删除，无须每点一次按钮就重复询问。
若实际发现新的域名、配置或第三方扩展，更新计划并补充确认后再扩大范围。

## 3. 逐配置执行原生 UI 清理

优先使用浏览器自己的设置页和扩展管理页，不能直接删除整个浏览器配置或共享数据库。
浏览器自动化连接若只暴露一个配置，也不代表其他配置已经处理。

对每个配置依次执行：

1. 通过配置切换菜单打开该配置的窗口，读取最新 UI 状态确认当前配置身份。
2. 不访问 Claude 官网，以免清理后重新生成站点数据。
3. 打开网站数据设置。Chrome 可尝试 `chrome://settings/content/all`；产品版本不同则使用设置中的“所有网站数据和权限”等入口。
4. 逐个搜索目标官方域，等待页面稳定，再读取当前结果。
5. 核对结果中的真实站点和子域。搜索命中并不等于可以删除。
6. 只删除已确认的官方域分组或站点项，在浏览器确认框中再次核对域名。
7. 如果界面提供“删除所有显示的数据”，只有所有显示结果都在白名单内才能使用。
8. 重新读取该域的结果；检查字节数、Cookie 数和仍显示的子域。
9. 分区 Cookie 可能出现在扩展或其他顶层站点分组中，展开并核对，不能把一个分组为空当作全配置为空。
10. 对三个官方域重复检查，然后再切换到下一个配置。

原生 UI 的元素编号、坐标或 DOM 引用会变化。切换配置、删除项目、关闭标签后必须重新获取状态。
使用工具提供的直接设置文本能力填写地址和过滤字段，避免剪贴板中已有的敏感文本被误粘贴。
若地址输入异常或设置页空白，打开新标签再导航到设置，不能把空白页面当作已清理。
每完成一个配置，更新“已清理 / 无数据 / 被阻止 / 未核验”的状态。

## 4. Claude 扩展实例

每个浏览器配置的扩展是独立实例。至少检查官方 Claude 扩展，以及用户确认范围内的 Session Key、会话切换等工具。
先从 UI 和本地 manifest 元数据核实名称、发布者、扩展 ID、安装类型、权限及用途。
名称相似不足以授权删除；不要删其他服务的 Cookie 工具、密码管理器或一般代理扩展。

执行步骤：

1. 在该配置打开扩展管理页，例如 Chrome 的 `chrome://extensions`。
2. 对计划中已核实的实例先停用，再选择移除，并确认准确名称。
3. 若卸载打开反馈网页，关闭网页；不要代用户提交反馈或个人信息。
4. 再次读取扩展列表，核实该实例已不在已安装列表中。
5. 只读检查该扩展 ID 对应的安装目录与独立存储目录是否仍存在。
6. 遇到组织策略强制安装的实例，报告受管理限制，不更改系统策略或绕过组织控制。

Chromium 可能留下空的扩展注册对象或仅有名称的完整性记录。
这不等于扩展仍安装；分别报告“实际安装/存储”和“空元数据残留”。
不能为删除空记录手工改写 `Secure Preferences` 或它的完整性校验信息。
系统级 Native Messaging Host 清单也不等于登录凭据；保留应用时通常保留，卸载应用另列计划。
同步可能重新安装扩展。核验并报告实际情况，不默认关闭整个浏览器同步或退出 Google 账号。

## 5. 清理后核验

至少提供逐配置的 UI 核验。能读取磁盘时再做只读复核，但不要输出或解密 Cookie 值。
允许读取的 Cookie 元数据通常只有主机、名称、分区顶层站点、数量和数据库结构。
常规盘点不得查询 `value`、`encrypted_value`，也不得导出登录凭据。

1. 保存浏览器当前窗口的恢复方式；在必要时正常退出浏览器，让数据刷盘。
2. 不用强制终止替代正常退出。核实浏览器主进程和相关后台进程均已停止。
3. WAL 活跃或进程未退出时，不能用 `immutable=1` 宣称读取了最新状态。
4. 使用只读 SQLite 连接读取一致状态；同时检查 WAL/SHM 是否影响结果。
5. 对官方域边界精确匹配，记录每域数量，不输出值。
6. 只读检查目标 origin 的 IndexedDB 目录与扩展独立目录是否存在。
7. 无法解析共享 Local Storage/Service Worker 时，只报告原生 UI 已删除；不能假装逐字节复核。
8. 重新打开浏览器，按支持的方式恢复用户窗口，不访问目标网站再核验。

最终表格应包含浏览器、配置、已处理官方域、目标 Cookie 数量、扩展状态、UI/磁盘核验方法和未处理项。
一项为空或没有权限时写明“未核验”，不能写成 0。

## 6. 仅在必要时：孤立分区 Cookie 修复

这不是常规步骤，也不是整库清理脚本。
只有原生 UI 删除、扩展卸载、正常退出及独立只读复核后，仍有已确定的孤立目标行时才考虑。
先提供追加计划，列出浏览器配置、数据库路径、非敏感目标元数据、精确行数、备份和回滚方式；用户确认后才能写数据库。
计划必须说明一致备份会包含该配置其他网站的 Cookie，须留在本机并限制访问权限。

修复前置条件：

- 浏览器及会修改此数据库的后台进程完全退出。
- 真实数据库 schema 已检查，目标定位列及唯一性已验证。
- 目标是官方域边界内的已识别行，分区信息明确；不能只按名称匹配。
- 使用 SQLite backup API 建立一致副本；如保存原文件，也保存所需 WAL/SHM，不能只拷主文件丢失已提交数据。
- 备份 `quick_check` 通过，目录与文件权限尽量限制为当前用户。
- 清理前已建立所有非目标行和 meta 表的本地保护摘要。

常见 Chromium 结构可用 `host_key + name + top_frame_site_key` 组合辅助定位，但必须以现场 schema 为准。
如果组合命中多行，应加上实际唯一键；不能把多行自动当作同一残留。
保护摘要需要在本机封闭校验进程内把非目标完整字段当作不透明字节进行确定性哈希。
值只用于比较，不查看、不输出、不解密、不发送给模型或网络；外显报告仅记录数量和“是否一致”。
若工具无法满足此要求，停止离线修复，只报告残留。

确认后执行单个受保护事务：

1. 连接前再次验证浏览器已退出、目标行数与确认计划一致。
2. 设置 `PRAGMA secure_delete=ON`，取得 `BEGIN IMMEDIATE` 锁。
3. 用参数化精确条件删除已确认行，检查实际删除数等于计划数。
4. 在提交前比较全部非目标行摘要和 meta 内容，检查目标行归零。
5. 任一不一致即 `ROLLBACK`，保留备份并报告，不继续扩大删除条件。
6. 满足条件后提交，执行 `quick_check`，再独立只读核验目标和保护摘要。
7. 恢复窗口，记录实际结果和备份位置。

不删除整张 `cookies` 表，不删除 `Cookies` 文件，不清空整个配置，不手工删除活跃 WAL/SHM。
`secure_delete` 只作用于 SQLite 页面，不保证 SSD、系统快照或其他副本的物理擦除。
不要把逻辑删除报告成无法恢复的安全擦除。

## 7. 其他浏览器与范围限制

Safari、Firefox、Edge、Brave 按实际配置逐一处理，优先使用本产品的网站数据与附加组件界面。
Safari 遇到系统隐私权限限制，报告缺少权限和未完成范围；不能关闭 SIP、修改 TCC 或宣称已完成。
Firefox 数据结构与 Chromium 不同，不能套用 Chromium Cookie SQL。
如果只有只读文件权限或没有可操作 UI，完成可做的盘点并保留待办，不创建绕过权限的方案。
历史记录、下载记录和保存密码不属于默认登录态重置；若用户另要求清理，先列出精确目标并确认。
默认保留备份；用户要永久删除时，按主流程的独立确认规则处理本次精确批次，不能清空全体废纸篓。
